## 方針と全体像

週1回×1時間×12回（約3か月）を基本形とします。目的は、Linux の基礎から始めて、配属後に知らない領域に触れたときの判断基準となるベースを作っておくことです。そのために、1つの題材を通して「作る」より「仕事を進める型」（記録する・小さく変更する・設計で合意する・テストで確かめる）を身につけ、知識体系マップで全体のどこに何があるかを押さえます。Web開発は手段であり、評価の中心はGit運用・設計書の質・テストのある実装に置きます。

- **1回の進め方**：冒頭の座学で要点をまとめて話し、ハンズオンの合間にも短い座学を挟みます。座学で使うのはハンズオン資料の「まとめ」か、参考書の該当章です。ハンズオンでは講師と一緒にその場で動かし、後半の回では各自が実際にプログラムを作ります。配分は回ごとに変え、「全N回の一覧」の所要の列に書きます。振り返り・宿題・発展課題は設けず、その回でやることは60分の中で終えます。
- **ハンズオン資料はチートシート＋ステップ**：まとめはエッセンス（コマンド・用語・判断の基準を表や箇条書きで）と、参考書と無料の公式資料への参照だけを載せます。ハンズオンは1ステップずつ「🖋 やること → 📚 参考書の節 → 📒 短い説明（Mermaid の図を多めに）→ コマンド」の形で書きます。副読本は全員が持っているとは限らないので、資料は副読本なしで完結させます。短く保ちつつ、その回に必要な要素は漏らしません。詳しい説明は本に任せます。
- **言語はPythonで統一**：言語の学習コストを抑え、設計・テストの学習に回します。Python は2回（第6〜7回）かけて基本から Python らしい書き方（ダックタイピングなど）まで扱い、第8回でテストを書けるようにします。Web は移り変わりが激しいため、HTTP・HTML・Cookie・WebSocket など変わりにくい基礎を厚く学びます。バックエンドは FastAPI、画面はサーバが HTML を返す軽い構成とし、React などのフレームワークやビルドツールは使いません。
- **受講者のレベル差**：情報系・非情報系の混在を想定し、ハンズオンを短いステップに分けて、全員がその場で同じところまで進めるようにします。
- **進め方**：全回を個人で進めます。共通のリポジトリは使わず、各自のリポジトリで作ります。Git で管理するのはコード・設計書など履歴を残す意味があるものだけにし、毎回の演習を必ず Git に載せることはしません。レビューは PR のセルフレビューと、講師や隣の人に見てもらう形で行います。
- **プロジェクトマネジメントは軽く**：作る機能をユーザーストーリーに分け、幅を持たせて見積もり、Issue で管理する考え方を体験する程度にします（第9回）。研修そのもの（講義やハンズオン）について見積と実績を記録する進捗管理は行いません。

画面側はライブラリを使わず、素の HTML と JavaScript（fetch）で作ります。ブラウザ標準の機能は流行に左右されず、通信を自分で書くので初学者でも何が起きているかを追えるからです。基本形は「サーバが HTML 断片を返し、JavaScript は受け取って差し替えるだけ」とし、画面の中身をサーバ側に残して pytest による TDD の範囲に収めます。第12回では1機能だけ JSON を返す版も書き、次の観点で比べます。htmx は最後に「この作りをライブラリにしたもの」として紹介します。

| 観点 | HTML 断片を返す（基本形） | JSON を返す（比較用） |
| --- | --- | --- |
| サーバが返すもの | Jinja2 で描いた HTML 断片 | JSON |
| 画面を組み立てる場所 | サーバ | ブラウザ |
| JavaScript の役割 | fetch して受け取った HTML を差し替えるだけ | JSON から DOM を組み立てる |
| 状態の持ち主 | サーバに一元化しやすい | ブラウザの変数とサーバで二重に持ちやすい |
| テスト | 返す HTML を pytest で検証でき、TDD の範囲に収まる | API は pytest で検証できるが、画面の組み立てはブラウザ側のテストが別に要る |
| 安全性 | テンプレートが自動でエスケープする | innerHTML に値を直接入れると XSS になる。textContent を使う |
| 向いている場面 | CRUD 中心の画面、管理画面 | 複雑なクライアント側の状態、オフライン対応 |

オンラインへのリリースは前提として設計に含めますが、実際には公開しません。第9〜10回の非機能要件とシステム構成図は本番公開を想定して書き、設定は環境変数で切り替えられるようにします。CI で PR ごとにテストを自動実行するところまでを扱い、デプロイや実際のリリースは行いません。

## 通しの題材と横断テーマ

題材は「TODO・タスク管理アプリ」です。第6〜8回で Python の CLI（追加・一覧・完了・期限）として作ってテストを付け、第9〜10回で Web 版の要件と設計を書き、第11〜12回で画面（FastAPI＋Jinja2＋SQLite＋素のHTML/JavaScript）をテスト付きで作ります。全員が個人で一通り作ります。

全回を貫く横断テーマは次の4つです。どの回でも必ず触れるので、個別の回で教え切る必要はありません。

1. **Git**：第5回以降、コードと設計書は自分のリポジトリにコミットし、まとまった変更は PR にしてセルフレビューしてからマージする
2. **ドキュメント**：設計書・README・手順書をリポジトリ内にMarkdownで置く。第9回で図と要件、第10回で設計書の書き方を学び、以降の回でも要所で Mermaid の図を書いて考え・伝える
3. **環境の再現性**：第4回以降、「自分のPCでは動く」を禁止。mise.tomlと手順書だけで他人が再現できることを完了条件にする
4. **TDD**：第8回以降の実装はテストを先に書く。テストのコミットと実装のコミットを分け、PR の履歴でレッド→グリーン→リファクタリングの順序が追えることをレビュー基準にする

## 知識体系とタグ

研修で扱う知識を4つの大分野に整理し、第1回の冒頭で全体地図として紹介します。大分野は知識の性質で分けており、コンピュータ基盤（動かす土台）、実装技術（作るための技術）、ソフトウェア開発（作り方と道具）、その他（プロジェクトマネジメント）の4つです。その下は書籍の守備範囲（章立て）に合わせて切っています。このため、枝ごとに「この本を読めばよい」と副読本を案内できます。知識体系は研修の回とは独立させ、回との対応は各回のアジェンダ側からタグで付けます。

枝は分野ごとに深さを変えてよく、必要に応じて何段でも伸ばせます。タグは大分野を除いた経路を「-」でつないだ名前（例：`http-リアルタイム`）とし、資料の粒度に合わせてどの深さのタグを付けても構いません（`http` のように途中の枝で止めてもよい）。同じタグ名をハンズオン資料と Issue ラベルで共通に使います。

図にしたもの：[研修で扱う知識の系統図](diagrams/knowledge-map.png)（`tools/` の `mise run diagrams` でこのマップから生成）

### 知識体系マップ（木構造）

### 設計書で押さえること（設計-要件・設計-構成・設計-詳細）

アジャイルで設計書を少なくする前提で、書くのは次の5つだけにします。何を作るかはユーザーストーリーと受け入れ条件で合意し、細かい振る舞いは TDD のテストで示します（画面設計書とテスト仕様書は作りません）。図は Mermaid で Markdown に書き、Git で差分を追える形にします。合格基準は「実装者が質問せずに作れるか」です。

| 設計書 | 主な図 | 必須記載事項 |
| --- | --- | --- |
| ユーザーストーリー（Issue） | — | 「〜として、〜したい。なぜなら〜」、受け入れ条件（チェックリスト）、幅のある見積 |
| 要件メモ | 業務フロー図 | 目的・背景、非機能要件（性能・セキュリティ・運用）、制約、対象外、ストーリー一覧へのリンク |
| API設計書 | シーケンス図 | エンドポイント、メソッド、リクエスト・レスポンス例、ステータスコード、入力チェックとエラー表示の文言 |
| DB設計書 | ER図 | テーブル定義（カラム・型・NULL可否・キー）、制約 |
| システム構成図 | 構成図 | 構成要素、通信経路とポート、ミドルウェアとバージョン |


## 各回の詳細

### 第1回　Linux の全体像

tag: `linux`　冒頭の座学で系統図と全体像の図を使って知識体系を紹介する。Linux は『入門 モダンLinux』の流れに沿って、全体を一度通して見る（各分野の深掘りは第2回以降）

- **狙い**：Linux がどんな部品でできているかの地図を持ち、黒い画面への抵抗をなくし、「何をしたか」を記録する習慣をつける
- **内容**：次の順に、参考書の節・短い説明・理解のためのコマンドの流れで進める
    1. 全体：カーネルとユーザー空間、WSL と Windows の関係（uname・/mnt/c）
    2. プロセス：プロセスと PID、シェルもプロセス、PID 1（init／systemd）、親子関係、ジョブとシグナル（ps・pstree・kill）
    3. ファイルシステム：ディレクトリの構成、すべてはファイル（/proc・/dev）、権限、標準入出力とリダイレクト・パイプ（ls・chmod・>・|・/proc/$$/fd）
    4. ネットワーク：TCP/IP の各層（リンク・インターネット・トランスポート・アプリケーション）と、各層を見るコマンド（ip・ping・ss・curl）
    5. ここまでで出なかったが押さえておくコマンド：grep・wc・sort・uniq・find・xargs・man
    6. コンテナ：namespace と cgroup、Docker の基本
    7. モダンなコマンド：ripgrep・fd・bat・fzf・jq など
- **演習**：ログファイル（講師配布）から grep と wc で特定のエラー件数を数える。振り返り・宿題・発展課題は設けない

### 第2回　シェル・環境変数・通信の切り分け

tag: `linux-シェル` `linux-アプリ` `linux-ネットワーク`　第1回で一度通したプロセス・ネットワークの層・DNS・curl -v は繰り返さず、シェル・パッケージ・通信の切り分けを深掘りする

- **狙い**：「コマンドが見つからない」「ネットにつながらない」を自力で切り分けられるようにする
- **内容**：次の順に、参考書の節・短い説明・理解のためのコマンドの流れで進める
    1. 変数：シェル変数と環境変数、export が効く範囲（子にはコピーが渡り、親は変わらない）
    2. PATH：コマンドを探す順番（エイリアス → 関数 → 組み込み → PATH）、type -a、自分のコマンドを PATH に足す、子のシェルで PATH を壊して戻す
    3. .bashrc：ログインシェルと対話シェルで読まれるファイル、コピーを取ってから追記し、わざと壊して直す
    4. apt と sudo：リポジトリ・apt update・install・dpkg -L、sudo で環境変数が消えること
    5. 通信の切り分け：curl の表示と終了コードで、名前解決（6）・接続（7・28）・TLS（60）・HTTP（404、-f で 22）のどこで止まったかを見分ける
    6. 社内で必要な設定としてのプロキシ：http_proxy／https_proxy／no_proxy（小文字と大文字）、http と https（CONNECT）の頼み方、apt の設定ファイル、社内CA証明書、git で確かめる
    7. 環境設定手順書を仕上げる：新しいターミナルで確かめ、元に戻す方法を書く
- **演習**：子のシェルと `.bashrc` で PATH を壊して直す／curl で各段階の失敗をわざと起こし、表示と終了コードを記録する。手順3から、打ったコマンドと確認方法をその場で環境設定手順書（第4回で隣の人が使う）に書く。振り返り・宿題・発展課題は設けない

### 第3回　Web 通信の基礎（HTTP・Cookie・Web API）

tag: `http` `web-ブラウザ` `sec`　第1回の `curl -v`（リクエスト行・ヘッダ・空行・本文）と第2回の切り分け・プロキシを前提に、届いた後のやり取りを深掘りする。mise・uv はまだないので、素材は Ubuntu の `python3` の標準ライブラリだけで動くデモのサーバ（`docs/session03/assets/web_demo.py`。このサイト 8000 と別のサイト 8001）にする

- **狙い**：ブラウザとサーバの間で何が起きているかを、ヘッダ・Cookie・Web API の実物を読んで説明できるようにする
- **内容**：次の順に、参考書・公式資料の節・短い説明・理解のためのコマンドの流れで進める
    1. デモのサーバとヘッダの中身：`curl -v` で Host・User-Agent・Accept・Cache-Control・Set-Cookie・Content-Type・Content-Length を読む、`curl -I`（HEAD）、`/headers` で送ったヘッダを見る
    2. Network タブ：document と stylesheet、再読み込みで `ETag`／`If-None-Match` の 304、ブラウザが自動で付けるヘッダ（Accept・Sec-Fetch-*・Cookie）
    3. Cookie とセッション：curl の `-c`・`-b`、Cookie の値を書き換えられること、ログイン（303 と Set-Cookie の属性 HttpOnly・SameSite・Max-Age）、Cookie の有無で変わる `/api/me`（401）、ログアウトでサーバのセッションを消す、ブラウザの「アプリケーション」と `document.cookie`
    4. CSRF：トークン付きのフォーム、`127.0.0.1:8001` の罠（同じサイト、403）と `localhost:8001` の罠（別のサイト、SameSite で Cookie が付かず 401）、オリジンとサイトの違い
    5. Web API と JSON：REST（URL はもの、メソッドはすること）、一覧・クエリ文字列・jq、POST の 201 と Location、PATCH・DELETE（204）、わざと失敗させる（415・400・422・405・404）、ETag の 304、公開 API（JSONPlaceholder）をプロキシ越しに呼ぶ
    6. CORS とプロキシ：別のオリジンからの fetch がブラウザで止まり、サーバには届いている（ログの Origin）、`Access-Control-Allow-Origin` で許可した API、curl では読める、`no_proxy` で 127.0.0.1 に直接つながる
    7. DOM・fetch・XSS をコンソールで：DOM の木、`textContent` の書き換え、fetch で追加して `<li>` を足す、`innerHTML` の XSS、エスケープしないページ（`/search-unsafe`）で `document.cookie` に HttpOnly の Cookie が出ないこと
- **演習**：デモのサーバと公開 API を相手に、上の流れでヘッダ・Cookie・JSON を観察する。成果物はない。振り返り・宿題・発展課題は設けない（プリフライト・GitHub の API の回数の制限は講師が見せる補足）

### 第4回　実行環境の整備（mise・uv）

tag: `env-mise` `env-python`　第2回の PATH・`.bashrc`・プロキシを前提に、Python とパッケージを OS から切り離してディレクトリごとに固定する。第5回でリポジトリにするファイル（mise.toml・pyproject.toml・uv.lock・main.py・環境構築手順書の README.md）は、すべてハンズオンの中で作る

- **狙い**：バージョン管理ツールで「誰でも同じ環境を再現できる」状態を作り、手順書だけで他人が再現できるかを確かめる
- **内容**：次の順に、参考書・公式資料の節・短い説明・理解のためのコマンドの流れで進める
    1. システムの Python：OS が使っていること、版が PC ごとに違うこと、`EXTERNALLY-MANAGED`（OS・ツール・パッケージの3つの層）
    2. mise を入れる：`.bashrc` のコピーを取って activate を書く。`cd` とプロンプトのたびに PATH が変わる仕組み。環境構築手順書のテンプレートをコピーし、ここから書きながら進める
    3. mise で固定する：`mise use --path .` で Python 3.12 と uv を `mise.toml` に書く、親の `mise.toml` との関係、`cd` で切り替わることを確かめる
    4. uv：`uv init`・`uv add`・`uv tree`、pyproject.toml と uv.lock と `.venv` の関係、`.venv` の中（mise の Python へのリンク）
    5. mise.toml の `[env]`（`UV_PYTHON_DOWNLOADS`・`.venv` の自動有効化）と `[tasks]`（setup・hello）。`requires-python` に上限を付け、`uv sync --locked` が止まるのを見て `uv lock` で直す

    5. 受け入れ条件 (15) を部分更新で試し直して不具合を見つけ、Issue #19（ラベル `不具合`）→ 不具合票 BUG-001 → 再現テスト（レッド）→ 修正（グリーン）→ PR #20 でマージ
    6. 発表準備：素材の発表資料の型（何を作ったか → 構成 → デモ手順 → 工夫1つ）を埋め、PR の数・レッドのコミット数・テストの件数を根拠に添える。デモを1回通し、PR #22 でマージ
    7. 発表：1人ずつ発表とデモ、聞き手は良かった点と質問を1つずつ。持ち時間は人数から講師が決める
- **演習**：上の流れを各自のリポジトリで通す。手で書くのは不具合票・再現テスト・修正と、発表資料の工夫の節。振り返り・宿題・発展課題は設けない（スクラムと KPT は扱わない。ポーリング・SSE・WebSocket・htmx は講師が見せる補足）
- **図**：ページと断片のテンプレートの関係、fetch で差し替えるシーケンス図、イベントの委譲、JSON 版のシーケンス図、不具合が出る画面の状態遷移図、不具合を直す流れ、TDD の履歴の gitGraph
- **SE観点**：不具合票の書き方（再現手順・期待結果と根拠・実際の結果）。発表では主張に根拠（テスト・PR・設計書・不具合票）を付ける
