## つまずきやすい点

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| ER図が描けない | テーブル名・カラム名に日本語や空白、`FK` の前に型がない | 英字にし、日本語は `"期限"` のように引用符の中に書く。1行は `型 名前 PK "説明"` の順 |
| シーケンス図の `alt` で描けない | `end` がない、`else` の後に条件がない | `alt` … `else` … `end` を1組で書く |
| 構成図のラベルで `Parse error` | `HTTP 127.0.0.1:8000` の中の記号や `:` | `-- "HTTP 127.0.0.1:8000" -->` のように `"` で囲む。`subgraph` の名前も `U["uvicorn 127.0.0.1:8000"]` の形にする |
| 状態遷移図や矢印のラベルの `<` が消えたり崩れたりする | Mermaid が HTML のタグの始まりとして扱うことがある | 全角の `＜` にするか、「期限の翌日になる」のように語で書く |
| DB設計書に `status` 列がある | 計算できる値を持とうとしている | 日付が変わるたびに書き換えが要ること、`done` と食い違う危険を説明し、「計算で求める値」の表に条件を書かせる |
| 期限切れの条件が「期限を過ぎたら」だけ | 境目（当日）と期限なしを決めていない | `done = 0` かつ `due` が NULL でなく `due < 今日` のように不等号まで書かせる。当日は期限切れではない |
| `due` の NULL の意味がない | NULL 可にしただけ | 「期限なし」と書かせ、並び順で最後になることも書かせる |
| `done` を TEXT や BOOLEAN にしている | SQLite の型を知らない | SQLite に真偽値の型はなく、0／1 の INTEGER で持つ。日付も ISO 8601 の TEXT |
| エラーがすべて 400 か 500 | ステータスコードの違いを知らない | まとめの表で「入力が悪い（400）」「無い（404）」を区別させる。500 はサーバの不具合で、設計で返すものではない |
| 追加の成功で 200 と一覧ページを返す | 303 の理由を知らない | まとめの「エンドポイント」の 303 の行と手順2の「POST の後は 303 で一覧へ戻す」で、再読み込みで二重に追加される流れを見せる |
| URL に動詞（`/addTask`・`/done?id=2`） | 操作を URL に入れている | URL は「何を」、メソッドは「どうする」。完了は「タスク2の完了」なので `/tasks/2/done` に POST |
| 入力チェックの文言が「エラーを出す」だけ | 画面設計書がなく、どこに書くかわからない | 「入力チェックとエラー表示」の表に、受け入れ条件の文言をコピーさせる。第11回のテストで同じ文言を確かめると伝える |
| 画面のレイアウトを描こうとして時間がなくなる | 画面設計書の代わりを作ろうとしている | 画面は作らない。レスポンス例（返す HTML の要点）で示せば足りる |
| 交換した相手にその場で口頭で答えてしまう | 質問に答えるのが親切だと思っている | 「次に読む人はあなたに聞けない」と伝え、答えは設計書に書かせる |
| 質問が出ない、または感想だけ | 何を見ればよいかわからない | 手順6の問いの表を1行ずつ設計書で答えさせる。答えに迷った行が質問になる |
| 手順7の `git diff` に何も出ない | 手順5のコミットをせずに見本をコピーした | 自分の版は上書きされて残っていない。見本のままコミットさせ、交換で出た質問だけ PR の本文に書かせる |
| `docs/stories.md` の Issue の番号が #8〜#11 に戻った | 第9回で番号を直した人が見本をコピーした | `git diff docs/stories.md` で一覧の表の番号を自分の番号に戻してからコミットする |

### 講師が見せる補足（任意）

時間が余ったときに講師の画面で見せます。受講者の課題にはしません。

- HTML 断片の URL: 第12回の見本（[session-12/docs/design/api.md](../../examples/todo-app-snapshots/session-12/docs/design/api.md)）で足される A-04〜A-07（`GET /fragments/tasks` など）を見せ、通常の送信は 303 → `GET /` でページ全体、fetch は断片を1往復で受け取る違いをシーケンス図で比べる
- タグの多対多: `tags`（`id`・`name` UNIQUE）と中間テーブル `task_tags`（`task_id`・`tag_id`、2つで主キー）に分ける。ER図は `tasks ||--o{ task_tags : ""`、`tags ||--o{ task_tags : ""`（副読本『達人に学ぶDB設計徹底指南書』4章）
- 完了済みをもう一度完了: 見本は何もせず 303 で `/` に戻す（何度送っても同じ結果になる操作）。409 にする案も理由があればよい
- `/tasks/abc/done` のように id が整数でないとき: FastAPI はパスの型の変換に失敗して 422 を返す。見本の設計書には書いていない。第11回で「設計書にない動き」の例として触れられる

## 評価の観点

- 設計書を読んだ隣の人が、質問せずに実装できたか（質問の数と中身で判断する）

- 出た質問への対応が設計書の 6章と PR の本文に書かれているか（書かなかった質問にも理由があるか）
