### この回の検証について

資料のコマンドは、Ubuntu 26.04（bash 5.3、curl 8.18.0、sudo-rs 0.2.13）で実行して確かめました。終了コード（6・28・60・22）、`-w` の各時間、`no_proxy` の有無による結果（000 と 200）、`Uses proxy env variable https_proxy` の行は実際の出力です。検証環境では、127.0.0.1 の閉じたポートへの接続がタイムアウト（28）になったため、拒否（7）の表示は curl 8.18.0 の通常の表示（`Failed to connect to 127.0.0.1 port 8000 after 0 ms: Could not connect to server`）を書いています。社内プロキシ経由の出力（`CONNECT`、apt、CA の登録）は、以前の版で CONNECT 対応のプロキシを手元で動かして確かめたものです。社内プロキシで実際に出るメッセージは確かめていません。

## つまずきやすい点

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `GREETING = hello` で `command not found` | `=` の前後に空白がある | 空白を入れない。シェルは `GREETING` をコマンド名として探した |
| 手順2で `exit` したらターミナルごと閉じた | `bash` で子のシェルに入る前に PATH を壊した | ターミナルを開き直せば戻る（export はそのシェルだけ） |
| 手順3で `.bashrc` の中身がすべて消えた | `>>` を `>` と打った | `cp ~/.bashrc.bak ~/.bashrc` で戻す。コピーを取っていなければ `cp /etc/skel/.bashrc ~/` で Ubuntu の初期状態に戻せる |
| どのターミナルを開いても `ls` が動かない | 壊す行を追記したまま、`sed -i '$d'` の前に新しいターミナルを開いた | `/usr/bin/sed -i '$d' ~/.bashrc` か `/usr/bin/cp ~/.bashrc.bak ~/.bashrc` とフルパスで打つ。`bash --norc` で `.bashrc` を読まないシェルも起動できる |
| `sed -i '$d'` で消したい行と違う行が消えた | 壊す行の後に別の行を追記した | `diff ~/.bashrc.bak ~/.bashrc` で差分を見て、`nano` で直す |
| `echo "export PATH=$HOME/mybin"` と二重引用符で書いた | 書き込む時点で `$HOME` が展開される | `.bashrc` に `/home/<ユーザー名>/mybin` と書かれる。単一引用符との違いとして説明に使える |
| `source ~/.bashrc` のたびに PATH が長くなる | 読み直すたびに先頭に足される | 害はない。新しいターミナルなら1つになる |
| `curl` は通るが `sudo apt update` が通らない | `sudo` が環境変数を引き継がない | 手順6の `/etc/apt/apt.conf.d/95proxy` を置く。`apt-config dump \| grep -i proxy` で読まれているか確かめる |
| `sudo -E apt update` でもプロキシが効かない | 新しい Ubuntu の sudo（sudo-rs）は `-E` を無視する | apt は設定ファイルで設定する。どうしても環境変数を渡すなら `sudo --preserve-env=http_proxy,https_proxy コマンド` |
| `apt update` で一部だけ失敗する | `Acquire::https::Proxy` を書いていない | https の行も書く |
| `HTTP_PROXY` だけ設定したら、http の URL で curl がプロキシを使わない | curl は安全上の理由で、大文字の `HTTP_PROXY` を読まない | 小文字の `http_proxy` も設定する |
| `curl: (60) SSL certificate problem: unable to get local issuer certificate` | 社内 CA が登録されていない | 手順6の CA の登録をする。DER 形式なら `openssl x509 -inform der -in <ファイル>.cer -out <ファイル>.crt` で変換してから置く |
| `update-ca-certificates` の結果が `0 added` | 拡張子が `.crt` でない、または DER 形式のまま | `head -1 <ファイル>` が `-----BEGIN CERTIFICATE-----` なら PEM |
| 手順5の `127.0.0.1:8000` で `Uses proxy env variable http_proxy` と出る | 先にプロキシを設定していて、`no_proxy` がない | `no_proxy` に `localhost,127.0.0.1` を入れる（手順6） |
| 手順5の `example.com` や `expired.badssl.com` が社内で 6 か 28 になる | 社内の DNS が外の名前を返さない、または外に直接出られない | 失敗でよい。どの段階で止まったかを言わせ、手順6の後にやり直させる |
| `kill %1` で `no such job` | `python3 -m http.server` を別のターミナルで起動した、または既に止まっている | `jobs` で確かめる。別のターミナルなら `Ctrl+C` で止める |
| `http.server` が `Address already in use` | 前のステップのサーバが残っている | `jobs` と `kill %1`、または `ss -tlnp \| grep 8000` で探して止める |

## 解答例

### 手順5で記録する表示と終了コード

| ステップ | 表示（curl 8.18.0） | 終了コード | 段階 |
| --- | --- | --- | --- |
| `nothing.invalid` | `curl: (6) Could not resolve host: nothing.invalid` | 6 | 名前解決 |
| `127.0.0.1:8000`（何も動いていない） | `curl: (7) Failed to connect to 127.0.0.1 port 8000 after 0 ms: Could not connect to server` | 7 | 接続（拒否） |
| `10.255.255.1` | `curl: (28) Connection timed out after 3002 milliseconds` | 28 | 接続（返事なし） |
| `expired.badssl.com` | `curl: (60) SSL certificate OpenSSL verify result: certificate has expired (10)` | 60 | TLS |
| `127.0.0.1:8000/nothing` | `< HTTP/1.0 404 File not found` | 0 | HTTP |
| 同上に `-f` | `curl: (22) The requested URL returned error: 404` | 22 | HTTP |

- 手順6の9番ポートのプロキシは `* Uses proxy env variable https_proxy == 'http://127.0.0.1:9'` の後に 7 で止まる。表示にあるのはプロキシのアドレスで、example.com ではない。「プロキシを設定したら、つながらない原因はまずプロキシ側を疑う」と結び付ける
- 7 と 28 の違い: 7 は相手（または途中の機器）が「待っていない」と返した。28 は返事がなく、途中で捨てられた。社内で外に直接出ようとすると 28 になりやすい

### 手順2・3の直し方（ほかの方法）

- 子のシェルで壊した PATH: `exit` する。親のシェルでも `export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` で一時的に直せる
- `.bashrc`: `/usr/bin/nano ~/.bashrc` で最後の行を消す、`cp ~/.bashrc.bak ~/.bashrc` で戻す、`bash --norc` で `.bashrc` を読まないシェルを起動してから直す

### 環境設定手順書

- 見本: [examples/session02/環境設定手順書.md](../../examples/session02/環境設定手順書.md)。手順7の後に見せる（先に見せると写すだけになる）
- テンプレートは `docs/session02/assets/環境設定手順書.md`。受講者は手順3で作業場所にコピーする
- 手順書で見るのは次の点
    - 手順ごとに「確認」があり、読み手が成功したかを自分で判断できる
    - プロキシのアドレスがプレースホルダーになっていて、パスワードが書かれていない
    - `.bashrc` を書き換える前にコピーを取る手順があり、PATH は元を残して足す書き方になっている
    - 「うまくいかないとき」が、表示と終了コードから止まった段階を引ける形になっている
    - 自分の環境でしか通じない書き方（自分のユーザー名入りのパス、「いつものフォルダ」など）がない
- 第4回の手順7で、隣の人がこの手順書の「確認」の行を打って前提がそろっているかを確かめる（第4回で隣の人と交換して再現するのは第4回の README）

### 講師が見せる補足（任意）

時間が余ったときに講師の画面で見せます。

```sh
# /etc/hosts に書いた名前は DNS より先に引かれる（WSL を起動し直すと消えることがある）
echo '127.0.0.1 todo.local' | sudo tee -a /etc/hosts
getent hosts todo.local
# プロキシを設定していると、no_proxy に todo.local がなければプロキシに送ってしまう

# ping は ICMP という HTTP とは別の通信。社内では止められていることが多い
ping -c 3 example.com    # 通らなくても、curl がプロキシ経由で通れば「つながっている」
```
