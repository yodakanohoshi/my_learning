# 研修の Git の規約（コミット・ブランチ・PR・セルフレビュー）

第5回から使う、研修共通の規約です。手順書のリポジトリ（`workspace/session05/`）と、第6回に作るアプリのリポジトリ（`workspace/todo-app/`）の両方で使います。第7回で自分のコーディング規約を決めるときに、見直してかまいません。

## 1. 1つのコミットには1つの目的だけを入れる

- 「何のための変更か」を1文で言えない変更は、コミットを分ける
- 例: 「手順書の追加」と「誤字の修正」は別のコミットにする
- 迷ったら小さく分ける。分けたコミットはまとめられるが、混ざったコミットを後から分けるのは難しい

## 2. メッセージは「1行目＝何を」「本文＝なぜ」

```text
README の mise のインストール手順に URL を追記する      ← 1行目: 何をしたか（日本語なら30文字程度まで）

隣の人に手順書を試してもらったとき、どこから入れるのかで  ← 本文: なぜそうしたか
迷ったため。                                            （1行目との間は1行空ける）
```

- 1行目は「〜する」の形で、そのコミットを入れると何が起きるかを書く
- 本文には、差分（`git diff`）を見てもわからないこと（理由、背景、試してやめたこと）を書く
- 1行目だけで理由まで伝わる小さな変更なら、本文は省略してよい
- 日本語で書く

## 3. コミットしないもの

| もの | 理由 | 対処 |
| --- | --- | --- |
| `.venv/` などの仮想環境 | `mise.toml` と `uv.lock` から作り直せる。ファイル数が多く、PC ごとに中身が違う | `.gitignore` に書く |
| `.env`、パスワード、トークン、プロキシの認証情報 | 履歴に一度入ると、後のコミットで消しても過去のコミットから読める | `.gitignore` に書く。入れてしまったら講師に相談し、パスワードを変える |
| `__pycache__/`、`tasks.json`・`var/` などの実行で自動でできるファイル | 作り直せる。実行するたびに変わる | `.gitignore` に書く |

## 4. コミットの前に確かめる

```sh
git status          # 意図しないファイルが入っていないか
git diff --staged   # これからコミットする差分
```

## 5. ブランチ運用

- main に直接コミットしない。main はいつでも動く・読める状態に保ち、変更はブランチ → PR → マージで入れる（例外は、リポジトリを作った直後の最初の数コミットだけ）
- 1 Issue = 1 ブランチ。名前は `issue-<番号>-<内容（英小文字とハイフン）>`（例: `issue-1-target-env`）
- ブランチは必ず最新の main から作る（`git switch main` → `git pull` → `git switch -c 名前`）
- ブランチは小さく短くする。放置するほど main との差が広がり、コンフリクトしやすい
- マージは既定のマージコミットで行う。マージしたブランチは消してよい

## 6. Issue と PR の書き方

| 項目 | 書くこと |
| --- | --- |
| Issue のタイトル | やることを「〜する」の形で |
| Issue の本文 | 目的（誰が何に困っているか）、完了条件（何ができていれば終わりか） |
| PR のタイトル | 何を変えたか（Issue のタイトルと同じでよい） |
| PR の目的 | なぜ必要か。`Closes #番号` で Issue と紐付ける（マージで Issue が閉じる） |
| PR の変更点 | 何を変えたか。変えていないことや、別の Issue で扱うことも |
| PR の確認方法 | 他人が同じ確認をできる手順と、期待する結果 |

テンプレート: [docs/templates/pull_request.md](../../templates/pull_request.md)。見本: [examples/session05/pr-description.md](../../../examples/session05/pr-description.md)

## 7. セルフレビューの観点

マージの前に、PR の差分（GitHub「Files changed」／GitLab「Changes」）を自分で上から読みます。他人のつもりで読み、気づいたことは行コメントに残します。

| 観点 | 見ること |
| --- | --- |
| 目的 | PR の目的と変更点が一致している。関係ない変更が混ざっていない |
| 確認方法 | 書いた手順を自分で実行し、書いたとおりの結果になる |
| 読みやすさ | 初めて読む人に伝わる。誤字や手順の抜けがない |
| 履歴 | コミットが「何を・なぜ」の単位に分かれている |
| 安全 | 秘密情報、`.venv/`、コンフリクトの記号（`<<<<<<<` など）が入っていない |

コメントは **事実**（どこで何が）・**理由**（なぜ気になるか）・**提案**（どうするか）をそろえ、先頭に `[必須]`（直してからマージ）／`[提案]`／`[質問]`／`[良い点]`／`[確認]`（確かめたこと）を付けます。見本: [examples/session05/self-review.md](../../../examples/session05/self-review.md)

## 8. コンフリクトの解決

- どちらかを選ばず、両方の Issue の目的が成り立つ形にする。片方を捨てると、その Issue は閉じても目的が失われる
- どちらの目的とも違う新しい案を思いついたら、この PR で決めずに新しい Issue にする
- 記号の行（`<<<<<<<`・`=======`・`>>>>>>>`）はすべて消し、`grep` で残っていないことを確かめてから `git add` する
- 解決したら PR の差分をもう一度セルフレビューしてからマージする

## 悪い例と良い例

| 悪い例 | 何が困るか | 良い例 |
| --- | --- | --- |
| `修正` | 何を直したのか、履歴から探せない | `README の uv のバージョン指定の誤りを直す` |
| `いろいろ` | 1つのコミットに複数の目的が混ざっている | 目的ごとに分けてコミットする |
| `README.md を変更` | ファイル名は `git log --stat` でわかる。何のための変更かがわからない | `README に mise install の手順を追記する` |
| `第4回の分` | 1つのコミットに複数の目的が混ざっている | `Python と依存パッケージのバージョンを固定する` |
| ブランチ名 `test`・`fix` | 何の作業か、どの Issue かわからない | `issue-3-proxy-note` |
| PR の本文が空 | 目的も確認方法もわからず、レビューできない | 目的（`Closes #3`）・変更点・確認方法を書く |
