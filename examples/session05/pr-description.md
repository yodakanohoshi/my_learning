# Issue と PR の説明の見本

演習の手順6〜7で作る、Issue #2 と、それを閉じる PR（#4）の説明の例です。PR は [PR テンプレート](../../docs/templates/pull_request.md) の項目で書いています。

## Issue #2

---

**タイトル**: 手順書のタイトルに所要時間の目安を書く

### 目的

手順書を開いてから「どのくらいかかるのか」がわからず、途中で時間切れになることがある。始める前に作業の時間を確保できるようにしたい。

### 完了条件

- README.md の1行目（タイトル）に所要時間の目安が書いてある

---

## PR #4

---

**タイトル**: 手順書のタイトルに所要時間の目安を書く

**ブランチ**: `issue-2-duration` → `main`

### 目的

手順書を始める前に、作業の時間を確保できるようにします。第4回に隣の人が試したときの実測（約30分）を目安として書きます。

Closes #2

### 変更点

- `README.md` の1行目の末尾に `（所要30分）` を足しました
- 対象の環境をタイトルに書く変更は #1（PR #3）で別に扱っています。この PR では変えていません

### 確認方法

1. このブランチの `README.md` を開く
2. 1行目が `# 環境構築手順（所要30分）` になっていることを確かめる
3. PR の差分が1行の変更だけであることを確かめる

### セルフチェック

- [x] 目的と変更点が一致している（関係のない変更が入っていない）
- [x] コミットが「何を・なぜ」の単位に分かれていて、メッセージで説明できている
- [x] 確認方法の手順を自分で一度実行した
- [x] 秘密情報や `.venv` などの不要なファイルが入っていない

---

### コンフリクトを解決した後に PR に足すコメント

> PR #3 のマージで同じ行が変わったため、`origin/main` を取り込んでコンフリクトを解決しました（a19a263）。
> 1行目を `# 環境構築手順（WSL の Ubuntu 向け・所要30分）` にし、#1 の対象の環境と、この PR の所要時間の両方を残しています。
> 確認方法の2は、この1行になっていることに読み替えてください。

## この見本のポイント

- **Issue** に「誰が何に困っているか」と、終わったかを判断できる完了条件がある
- **目的** に理由と根拠（実測）があり、`Closes #2` で Issue と紐付いている
- **変更点** に「変えていないこと」と、関係する別の Issue（#1）が書いてある。後から読んだ人が「対象の環境も書くべきでは？」と迷わずに済む
- **確認方法** が番号付きで、期待する結果まで書いてある。自分でも他人でも同じ確認ができる
- コンフリクトを解決したら、何をどう解決したかを PR にコメントで残す。PR の説明（確認方法）と実際の差分がずれたままにしない
