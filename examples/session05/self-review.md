# セルフレビューの見本

マージの前に、自分の PR の差分（GitHub「Files changed」／GitLab「Changes」）を読んで残すコメントの例です。自分の PR は承認（Approve）できないことが多いので、確かめたことと気づいたことを行コメントや「Comment」で残します。観点は [規約の「セルフレビューの観点」](../../docs/session05/assets/commit-convention.md#7-セルフレビューの観点) です。

先頭に `[必須]`・`[提案]`・`[質問]`・`[良い点]`・`[確認]` を付け、**事実・理由・提案** をそろえます。

## 良い例

> **[確認]** 確認方法の手順1〜3を実行し、`README.md` の1行目が `# 環境構築手順（所要30分）` になっていること、差分がこの1行だけであることを確かめました。

- 何を確かめたかが具体的で、後から読んだ人も同じことを確かめられる

> **[必須]** `README.md` 1行目: 所要時間は書けているが、「30分」が何の時間か（mise のインストールから `mise run hello` まで）がわからない。
> 読む人が「プロキシの設定も含むのか」で迷いそう。
> 本文の最初の段落に「mise のインストールから `mise run hello` まで」と書き足すコミットを、この PR に足してからマージする。

- 自分の PR でも、直さないとマージしないものは `[必須]` にして、直すコミットを足してからマージする
- どこで（事実）・なぜ（理由）・どうする（提案）がそろっている

> **[提案]** プロキシの設定がまだの人はもっとかかる。今回は目安なのでこのままにし、所要時間の内訳は別の Issue（#5）にする。

- この PR の目的から外れることは、PR を広げずに Issue に切り出す

> **[良い点]** コミットが1つで、メッセージの本文に「始める前に時間を確保できるようにする」と理由が書けている。`git log` だけで目的が追える。

- 良い点も具体的に書く。次の PR でもまねできる

### コンフリクトを解決した後

> **[確認]** マージコミット a19a263 の差分で、1行目が `# 環境構築手順（WSL の Ubuntu 向け・所要30分）` になり、#1 と #2 の両方の変更が残っていることを確かめました。`grep -n '^<<<<<<<\|^=======\|^>>>>>>>' README.md` は何も出ませんでした。

- 解決したら差分をもう一度読む。記号の消し忘れと、片方の変更の消し忘れを確かめる

## 直したほうがよい例

| コメント | 何が足りないか | 直した例 |
| --- | --- | --- |
| OK | 何を確かめて「OK」と判断したかがわからない | **[確認]** 確認方法の手順どおりに実行し、1行目が期待どおりであることを確かめました |
| （コメントなしでマージ） | セルフレビューした記録が残らない | 確かめた観点を1行書いてからマージする |
| あとで直す | いつ・何を直すのかが残らず、忘れる | **[提案]** 内訳の追記は #5 に切り出しました |
| ついでに誤字も直した | 目的と関係ない変更が混ざり、PR の目的と変更点がずれる | 誤字は別の Issue とブランチで直す。この PR からは外す |
