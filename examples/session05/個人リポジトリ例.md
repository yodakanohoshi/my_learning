# 個人リポジトリの例（第5回の演習を終えた時点）

> 見本です。コミット ID（左の英数字）と日時は人によって違います。作者は例示用の `trainee` です。

## ファイル構成

```text
workspace/session05/            ← 手順書のリポジトリ
├─ .gitignore
├─ README.md                    第4回の環境構築手順（1行目は演習で2つの Issue に沿って直したもの）
├─ mise.toml                    第4回
├─ pyproject.toml               第4回
├─ uv.lock                      第4回
└─ main.py                      第4回
```

`.venv/` は手元にありますが、`.gitignore` に書いてあるのでリポジトリには入っていません。`git ls-files` を実行すると、リポジトリに入っているファイルだけを確かめられます。

```console
$ git ls-files
.gitignore
README.md
main.py
mise.toml
pyproject.toml
uv.lock
```

## Issue と PR

| 番号 | 種類 | タイトル | 状態 |
| --- | --- | --- | --- |
| #1 | Issue | 手順書のタイトルに対象の環境を書く | PR #3 のマージで閉じた |
| #2 | Issue | 手順書のタイトルに所要時間の目安を書く | PR #4 のマージで閉じた |
| #3 | PR | 手順書のタイトルに対象の環境を書く（`issue-1-target-env` → `main`） | マージ済み |
| #4 | PR | 手順書のタイトルに所要時間の目安を書く（`issue-2-duration` → `main`） | コンフリクトを解決してマージ済み |

GitHub では Issue と PR の番号が共通なので、PR は #3・#4 になります。GitLab では Merge Request が `!1`・`!2` と別の番号になります。

ここで見てほしいこと:

- 最初のコミットが `.gitignore` です。`.venv/` や `.env` が一度も履歴に入っていません
- 最初の4つ（リポジトリを作った直後）のあとは、main への変更がすべて `Merge pull request` を通っています。main に直接コミットしていません
- `issue-1-target-env` と `issue-2-duration` は、どちらも `088f8f3`（同じ main）から分かれています
- `a19a263` が、2本目のブランチで main を取り込んでコンフリクトを解決したマージコミットです

## 本文に「なぜ」を書いたコミット

```console
$ git log -1 664855c
commit 664855ce17f9fd569f6062fd267966eeaa98ba24
Author: trainee <trainee@example.com>
Date:   Mon Oct 12 23:42:06 2026 +0900

    Python と依存パッケージのバージョンを固定する

    README の手順どおりに進めれば、誰の PC でも同じバージョンになるようにする。
```

差分を見れば「何を変えたか」はわかりますが、「なぜ」はメッセージに書かないと残りません。半年後の自分や、レビューする人のために書きます。

## コミットメッセージの比較

同じ変更に付けたメッセージの、悪い例と良い例です。

| 悪い例 | 何が困るか | 良い例 |
| --- | --- | --- |
| `第4回の分` | 手順書・バージョンの固定・動作確認用のコードという3つの目的が1つのコミットに混ざる | 3つに分け、`第4回の環境構築手順書を追加する` などを付ける |
| `修正` | 何を直したのか、`git log --oneline` で探せない | `手順書のタイトルに対象の環境を書く` |
| `README.md を更新` | ファイル名は `git log --stat` でわかる。何のための変更かがわからない | 同上 |
| `gitignore` | 何を管理から外したのか、なぜなのかがわからない | 1行目 `.venv と .env を Git の管理から外す`、本文に理由 |
| `Merge branch 'main' into ...` を手で書き換えて `コンフリクト修正` | どのブランチを取り込んだのかがわからなくなる | マージコミットは `git commit --no-edit` で既定のメッセージのままにする |
